    Capability combinations

    Page Summary

    Some risks belong to no single capability. They arise only when a system holds several capabilities at once. This page explains how ARC handles them: composite risks in the register, a check that reads a system's capabilities and reports whether a dangerous combination is present, and a control that breaks the combination. The lethal trifecta is the worked example.

    Why combinations matter

    ARC assesses a system one element at a time. Each capability brings its own risks, and each risk has its own controls. That works when the risks are independent of each other.

    Some are not. Consider three agents:

    • An agent that only browses the web can be misled by what it reads, but it holds nothing worth stealing.
    • An agent that only reads internal files holds sensitive data, but no outsider can give it instructions.
    • An agent that does both can be told by a web page to open a file and send its contents to an address the attacker chose.

    The third agent has a risk that neither of the first two has. Each of its capabilities can be well controlled on its own terms, so an assessment that looks at one capability at a time can pass a system that is exposed.

    Other fields met this problem long before agents did. Auditors use segregation-of-duties matrices to find duties that no one person should hold together. Security researchers wrote rules for dangerous combinations of app permissions on mobile phones. Cloud security tools flag "toxic combinations" of findings that are minor alone. ARC applies the same idea to the capabilities of an agentic system.

    What ARC builds in

    Composite risks. A risk in the register can list more than one element, and it applies only when the system has all of them. Components and design elements are present in every agentic system, so a composite risk that lists one of them depends on its capabilities alone. The register has these composite risks:

    Risk Applies when the system has all of
    RISK-012 Cascading errors in multi-agent architectures Agentic Architecture (DSN-01) + Agent Delegation (CAP-02)
    RISK-013 Man-in-the-middle attacks between agents Agentic Architecture (DSN-01) + Agent Delegation (CAP-02)
    RISK-047 Data exfiltration through combined access to untrusted content, sensitive data, and an outbound channel Internet and Search Access (CAP-07) + File and Data Management (CAP-11)
    RISK-049 Escape from evaluation or sandbox containment onto live systems Roles and Access Controls (DSN-02) + Code Execution (CAP-10)
    RISK-051 Unsanctioned coordination between agents Agentic Architecture (DSN-01) + Agent Delegation (CAP-02)
    RISK-055 Data exfiltration through message and API channels Other Programmatic Interfaces (CAP-09) + File and Data Management (CAP-11)

    A combination check. A composite risk names specific elements, so it cannot say "any capability that can send data out". The check fills that gap. For each combination ARC checks, the register records which capabilities can supply each part of it, and the check reports whether a system's capabilities complete the combination. The data is in combinations.yaml, next to the risks and controls.

    A control that breaks the combination. Each checked combination has a control. The verdict of the check decides whether that control must be implemented or can be waived. The check does not add or remove risks.

    Register 1.3 checks one combination, the lethal trifecta.

    The lethal trifecta

    An agent holds the lethal trifecta, a term coined by Simon Willison, when it has all three of the following:

    1. Untrusted content. Content that someone outside the organisation's control can write reaches the agent.
    2. Sensitive data. The agent can read data that would cause harm if it left the organisation.
    3. An outbound channel. The agent can cause data to reach a destination outside the organisation's control.

    LLMs cannot reliably tell instructions from data, so text in a web page, an email, or a document can direct an agent that reads it. With all three legs in place, one injected instruction is enough. The agent reads the sensitive data and sends it out through a channel it is allowed to use. No control is bypassed, because every step is something the agent is permitted to do.

    This has happened. In EchoLeak, a single crafted email led Microsoft 365 Copilot to send internal data to an attacker. In ForcedLeak, instructions in a web-form submission led Salesforce Agentforce to send out customer records. The Frontier Model Forum's brief on agent security recommends that, in higher-risk uses, no agent hold all three. Meta's Agents Rule of Two gives similar advice.

    Which capabilities supply each leg

    A capability can supply a leg wherever it is present, or only in some deployments.

    Capability Untrusted content Sensitive data Outbound channel
    Planning and Goal Management (CAP-01) – – –
    Agent Delegation (CAP-02) Maybe – Maybe
    Tool Use (CAP-03) – – –
    Multimodal Understanding and Generation (CAP-04) Maybe – Maybe
    Official Communication (CAP-05) Maybe – Yes
    Business Transactions (CAP-06) – Maybe Yes
    Internet and Search Access (CAP-07) Yes – Yes
    Computer Use (CAP-08) Yes Yes Yes
    Other Programmatic Interfaces (CAP-09) Maybe Maybe Maybe
    Code Execution (CAP-10) Maybe – Maybe
    File and Data Management (CAP-11) Maybe Yes –
    System Management (CAP-12) – Yes Maybe

    Yes means the capability supplies the leg wherever it is present. Maybe means it depends on the deployment, and the notes below say when. Planning and Goal Management and Tool Use supply no leg by themselves.

    When each capability supplies a leg

    Untrusted content. Content that someone outside the organisation's control can write reaches the agent.

    • Agent Delegation (CAP-02): maybe. Yes if it takes output from agents that other parties operate, or from agents that read untrusted content themselves.
    • Multimodal Understanding and Generation (CAP-04): maybe. Yes if its users are members of the public, or can upload or paste documents, images, or audio that someone else wrote.
    • Official Communication (CAP-05): maybe. Yes if it also reads replies or other inbound messages on the channels it sends through.
    • Internet and Search Access (CAP-07): yes. Web pages and search results can be written by anyone.
    • Computer Use (CAP-08): yes. Whatever appears on screen reaches the agent, including web pages, emails, and documents written by others.
    • Other Programmatic Interfaces (CAP-09): maybe. Yes if any API, queue, or mailbox it reads carries content from outside parties, such as inbound email, support tickets, form submissions, or webhooks.
    • Code Execution (CAP-10): maybe. Yes if it runs or reads code, packages, or repositories that outside parties can change.
    • File and Data Management (CAP-11): maybe. Yes if any file or data store it reads holds content from outside parties, such as uploads, shared drives, or records created from customer input.

    Sensitive data. The agent can read data that would cause harm if it left the organisation, such as personal data, credentials, or confidential records.

    • Business Transactions (CAP-06): maybe. Yes if it holds payment credentials, or can read account, order, or customer records.
    • Computer Use (CAP-08): yes. It can see whatever the signed-in user can open on the machine.
    • Other Programmatic Interfaces (CAP-09): maybe. Yes if any API it can call returns personal, confidential, or credential data.
    • File and Data Management (CAP-11): yes. It reads the organisation's files, databases, or knowledge bases.
    • System Management (CAP-12): yes. System administration reaches configuration, credentials, and logs.

    Outbound channel. The agent can cause data to reach a destination outside the organisation's control.

    • Agent Delegation (CAP-02): maybe. Yes if it can pass data to an agent that another party operates, or to an agent that has an outbound channel of its own.
    • Multimodal Understanding and Generation (CAP-04): maybe. Yes if its output is shown to people outside the organisation, or is rendered in a way that loads external images or links.
    • Official Communication (CAP-05): yes. It sends messages to people outside the organisation.
    • Business Transactions (CAP-06): yes. Transactions carry data to external parties in payment references, order details, and booking fields.
    • Internet and Search Access (CAP-07): yes. Any request to a web address can carry data in the URL or the query.
    • Computer Use (CAP-08): yes. It can use any application on the machine that sends data, including the browser and the mail client.
    • Other Programmatic Interfaces (CAP-09): maybe. Yes if any API it can call writes to a system outside the organisation, or accepts a destination that the agent chooses.
    • Code Execution (CAP-10): maybe. Yes if the environment its code runs in can make network requests.
    • System Management (CAP-12): maybe. Yes if it can change network, sharing, or access settings so that data becomes reachable from outside.

    Components are not in the table. Persistent memory can carry untrusted content or sensitive data from one session into a later one, so count what memory holds when you answer for each leg.

    The verdict

    Verdict When What to do
    Present Every leg is supplied by a capability marked Yes Implement the control below
    Possible Every leg is supplied, but at least one only by capabilities marked Maybe Answer the note for each of those capabilities from the system's code and configuration. If every leg is confirmed, implement the control. If a leg is absent, waive the control and record the evidence
    Not present At least one leg is supplied by no capability Waive the control wherever it is listed, and record which leg is absent

    The control is:

    CTRL-0097 (Level 0 · Cardinal). Do not give one agent untrusted content, access to sensitive data, and an unrestricted outbound channel at once; remove one, or gate the outbound channel outside the agent.

    It is a Level 0 control. Scoring does not waive it. It is waived only when a leg is absent, in the same way that any Level 0 control is waived when the capability or component it concerns is not present.

    There are three ways to break the combination:

    • Split the agent. Give the untrusted content to a separate agent that has no access to sensitive data and returns only structured values.
    • Remove the data. Take away the sensitive data that the task does not need.
    • Gate the channel. Restrict the outbound channel outside the agent. Limit recipients and destinations to a fixed allowlist, and require human approval for any message or call that carries data to a new recipient.

    The verdict describes the system as a whole. The control applies to each agent, so in a multi-agent system, record which agent holds each leg. Splitting the legs across agents satisfies the control only if the agent that reads untrusted content cannot pass free text to the agent that holds the data or the channel.

    Worked examples

    These are the systems from the guide for AI developers, with a simple question-answering bot for comparison.

    System Capabilities Verdict Why
    Question-answering bot CAP-04 Not present Nothing supplies sensitive data
    Agentic fact checker CAP-01, 02, 03, 04, 07, 11 Present Internet and Search Access supplies untrusted content and an outbound channel; File and Data Management supplies sensitive data
    Agentic coding assistant CAP-01, 02, 03, 04, 10, 11 Possible File and Data Management supplies sensitive data. Untrusted content depends on whether it reads repositories or packages that others can change. An outbound channel depends on whether its code runs with network access
    Agentic call assistant CAP-01, 02, 04, 06, 09, 11 Possible File and Data Management supplies sensitive data, and Business Transactions supplies an outbound channel. Untrusted content depends on what its callers and the systems it reads can put in front of it

    Using the check in an assessment

    • In the developer guide: the check is part of Step 2, after the applicable risks are listed.
    • In the assessment template: Section 2a records the verdict, the answer for each leg, and how the combination is broken.
    • With a coding agent: the ARC assessment skill runs the check. arc.py assess prints the verdict and the notes to answer for the capabilities given.

    Limits

    • One combination. Register 1.3 checks the lethal trifecta only. Capabilities combine in other ways too, for example when code execution gives an agent abilities that its tool list does not show. These are being studied for version 2.0.
    • Capabilities are coarse. Internet and Search Access covers reading pages and posting to them. Many systems will therefore get a verdict of Possible, and the notes turn that verdict into questions that evidence can answer.
    • Composite risks need every element. RISK-047 covers the trifecta through web access, and RISK-055 covers it through messages and APIs. Other routes, such as Computer Use alone, are caught by the check and not by a composite risk. Rules of the form "any capability that supplies this leg" are planned for version 2.0.
    • Design time only. The check reads what a system can do, not what it does in a given session. CTRL-0090 covers enforcement at run time.
